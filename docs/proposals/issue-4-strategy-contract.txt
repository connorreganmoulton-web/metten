METTEN STRATEGY IMPORT — PROPOSED CONTRACT
Revision 3 • 13 November 2026 • proposal only; not approved or implemented

1. Decision and scope
Give authors a documented, bounded set of observations, calculations and stateful rules they can combine through JSON. Do not hard-code D/E/F strategy names, old thresholds or a universal sample count. Quantity is a run setting. Strategy purchase-price conditions and the user's permitted purchase-price range must both hold.
Issue #4 implements validation, controlled evaluation, generated explanations, immutable local versions and the desktop import/edit flow. It does not implement feeds, execution, financial runs, qualification, live tests or a full old-bot clone. This proposal supersedes the unfinished local grammar draft if approved. Source/feature names are supported contract identities, not proof of working connections. Issue #5 supplies feeds; unavailable capabilities block starting a dependent run rather than silently substituting another source.

2. Named observations
Each input has a unique identifier, a fixed supported source and field, an explicit unit/type, and side where applicable. No user-supplied URLs, executable code, opaque external scores or credentials.
Source catalog:
- kalshi.contract: YES/NO best bid, buyable ask, last executed trade price, best-level available quantity, depth available through a named price limit, cumulative traded contracts, open interest. Last trade is historical execution, not a quote. A last-trade record is keyed by trade ID/time; stale last trades cannot count as fresh book observations.
- kalshi.market: market open/close UTC times and verified strike/target with contract identity. Do not assume missing metadata supplies a target or equate close with settlement.
- kalshi.brti: raw BTC reference and documented trailing-60-second average as separate fields. Neither is silently treated as final settlement; final-minute/settlement estimation is deferred until exact contract correspondence is verified.
- coinbase.btc_usd and kraken.btc_usd: explicitly named best bid, ask, midpoint and last trade in USD/BTC. Midpoint requires a coherent valid bid/ask pair. Never silently substitute spot for BRTI or one venue for another.
Fixed field documentation specifies provider origin and whether a value is observed or derived. The canonical kalshi.contract buyable ask is always derived from the opposite side of the same coherent order book: 1 USD/contract minus its best bid, with that opposing level’s quantity. Native ticker ask is a separately named summary field, not a fallback for this executable-book field; mismatches do not choose the cheaper quote. Missing opposing liquidity means missing ask. Quote quantities use contracts for Kalshi and BTC for spot; they cannot be compared as the same unit. No claim that listed fields are available without access/licensing verification.
Decimal constants are JSON decimal strings (no exponent) at documented precision; reject excess precision rather than round an author's limit. USD/BTC and USD/contract are distinct units. Contract prices allow subcent precision (up to four dollar decimals, bounded [0,1]); quantities are nonnegative fixed decimals; time uses integer milliseconds; percent means percentage points (0.03 means 0.03%, not 3%). Use checked arithmetic, not binary floating-point price comparisons. All percent-typed outputs as well as constants use percentage points (3 means 3%, not 0.03). The normative operation reference in section 3a defines calculations and precision; comparisons use that representation and explanations state it. Nonfinite/out-of-range data is unknown, not a matching value.

3. Supported calculations
Allow these for contract prices and BTC-price fields where units permit:
- Signed difference and percentage difference between compatible inputs, including source versus strike and Coinbase versus Kraken. Percentage denominator must be positive; otherwise unknown. Absolute value is available.
- Change in value and percentage return over an author-selected duration.
- Time remaining to close and elapsed time since open/checkpoint.
- Rolling arithmetic mean, minimum, maximum, range and population standard deviation of sampled values. Volatility in this version means population standard deviation of successive simple percentage returns, not annualized volatility or an undocumented confidence score.
- Crossing above/below a declared level, and rolling crossing count. Levels can be a compatible input, calculated value or constant.
- Contract spread (ask minus bid), total available depth through a price cap and rolling traded-contract volume from distinct trade events. Depth is not a fill guarantee. Sufficient executable depth for the user's quantity is an engine check; an author may additionally require a minimum visible quantity without setting order size.
All calculations form a bounded acyclic graph. No loops, recursion, arbitrary formulas, machine-learning uploads or generic evaluation language. Fixed listed operations only. Incompatible units/types are rejected. A negative spread is invalid book data, not an opportunity.
No calibrated probability/confidence model in this version: supporting the old D measurement families does not reproduce its proprietary-to-that-code scoring weights, candle score or exact decision. Reproducing that model needs a separately defined capability, not an arbitrary author-supplied score. This is an explicit limitation for owner review.

3a. Normative numeric operation reference
Constants/observations are typed finite decimal strings; no automatic currency conversion or percent/fraction conversion. BTC prices and USD/contract prices are positive/nonnegative as specified above; other signed quantities allow -1,000,000,000 through +1,000,000,000 in their own units. Source quantities allow at most eight decimal places; constants allow eight except price fields with tighter declared precision. IDs reference typed expressions, not free text formulas. Times remain exact integer milliseconds bounded by the market window.
Fixed-scale reference: numeric values are signed integer atoms at scale S=100,000,000 per declared unit, with absolute numeric magnitude <=1,000,000,000. Times/counts remain integers. Each node consumes quantized inputs and produces eight-decimal output with nearest, ties-to-even; publish these boundaries in the field reference. Use checked signed 256-bit INTEGER intermediates for the following bounded sums/products; no accumulated exact rational denominators. Narrower machine-word limits cannot change results. Unsupported magnitude, zero denominator or semantic intermediate overflow yields unknown with a reason, never wraparound. For primitive division, round the exact integer numerator/positive denominator directly to the destination atoms; no intermediate binary float determines comparisons.
For level statistics with atom values a_i and n<=10,000: mean_atoms=round_even(sum(a_i)/n); variance numerator D=n*sum(a_i*a_i)-sum(a_i)^2; population_stddev_atoms=round_even(sqrt(D)/n). Do not round variance before taking its root. For exact root rounding, set k=floor(sqrt(D)/n), compare 4*D with n*n*(2*k+1)^2, and select k or k+1; equality selects the even integer. These integer expressions fit the stated bound for valid capped inputs/counts. For volatility, FIRST quantize each adjacent return in percentage-point atoms using round_even(100*S*(b-a)/a), a>0, and enforce the same magnitude bound, THEN use that integer-return sequence in the same population-standard-deviation formula. This operation-specific return rounding is intentional and explained; sub-resolution differences can round to zero volatility. No claim of additional statistical precision.
Each simple percent/difference/change expression is rounded once at its output. The formulas below describe its intended mathematical units; the fixed-scale steps above are normative for variance/volatility rather than an ever-growing exact-fraction calculation.
- difference(A,B) = A-B, same units; percent_difference(A,B) = 100*(A-B)/B, output percentage points, B>0 required. Operand order is declared, not inferred. absolute(A)=|A|.
- change(X,W)=X(t)-X(t-W); percent_return(X,W)=100*(X(t)-X(t-W))/X(t-W), positive denominator required.
- mean(x[1..n])=sum(x)/n; minimum/maximum take observed grid values; range=max-min. Level population_stddev=sqrt(sum((x-mean_exact)^2)/n), using the bounded integer D formula above, not a rounded mean. Output has the level’s unit.
- volatility: form each adjacent grid return r_i=100*(x_i-x_(i-1))/x_(i-1), with positive denominator, rounded to percentage-point atoms BEFORE population standard deviation as specified above; round the final root to atoms. Output percentage points; no annualization. At least two returns required.
- spread=canonical ask-best bid in USD/contract; negative is invalid. Depth-through-cap sums opposing-book quantities at buyable prices <=cap, inclusive; missing levels/continuity do not imply zero available quantity. Exhausted, complete empty book establishes zero. Insufficient/truncated depth yields unknown when the query cannot be proven complete through cap. Rolling trade volume sums unique non-block trade quantities with event receipts in the declared window; no subtraction of resetting counters.
- crossing count is an integer count; confirmations and source IDs are not numeric prices. Integer counts can be compared to nonnegative whole-count constants only. Division by zero, missing inputs, invalid ranges or coverage failures yield unknown and a diagnostic, never zero or an invented price.

4. History, event ordering and crossing semantics
Every input event carries source identity/epoch, complete-event ID, source timestamp, monotonic engine receipt/evaluation timestamp and a unique monotonically increasing engine sequence number. The engine journal’s sequence is the authoritative total order across sources; provider timestamps do not reorder decisions. Determinism means identical ordered engine input journals and versioned validity profiles yield identical results, not that different arrival interleavings must give identical decisions. Replaying just per-source timestamps is insufficient evidence. All evaluation uses the as-received state; source timestamps check age/coherence. Reject duplicate IDs, out-of-order source sequences, source timestamps in the future or regressing within an epoch; report a continuity gap and reset incomplete temporal evidence as applicable. A late event never revises a completed sample, crossing, checkpoint, consumed opportunity or decision. Accepted late data can affect only subsequent evaluations if still valid under the pinned profile.
At receipt time T, first expire intervals, deadlines, stale values and continuity-dependent confirmation through T. Next apply complete source events with receipt time T in engine-sequence order; after each, recompute instantaneous features, process checkpoints in declaration order, and evaluate branches in priority order. Finally calculate all due grid features at T in dependency order into a staged snapshot, then atomically commit the entire T snapshot BEFORE dispatching any grid-triggered checkpoint or branch. The T grid evaluation is one frame whose trigger set contains every due grid ID: process matching checkpoints once in declaration order, then matching branches once in priority order. Independent grid publication order cannot expose a mix of old and new T features. Feature values not due at T retain their last published value with explicit timestamp/validity. The journal records the grid-frame finalization position; a later-received event cannot revise a finalized frame, even if it shares a millisecond timestamp. Grid samples strictly before T finalize before these events, using only earlier accepted state. Thus events accepted before the T frame closes are visible to that frame; an event received after T cannot revise it. Grid publication is not a provider update. A timer at T performs expiry and scheduled samples only; it never advances an event-count or first-event gate. Boundary end/close remains exclusive, even for an event received exactly then. The controlled clock and engine sequence reproduce this ordering without a real provider.
Each rolling/lookback feature explicitly declares mode=grid and period in whole milliseconds (minimum 100 ms). Window W must be positive, an exact multiple of period, strictly less than the 900,000-ms market duration, and W/period+1<=10,000. Reject invalid/unreachable durations at import with a field-path error; no 24-hour features or cross-market history in v1. Statistical windows use (t-W,t]; change additionally uses the endpoint t-W. Sampling anchored at market open. Use only accepted values with receipt time <=t whose original source timestamps remain age-valid under the pinned validity profile. Held still-valid values satisfy level-statistic grid coverage, but do not create distinct events. Explain sample-and-hold and the chosen period; a flat held mean/range is not evidence of independent observations.
All scheduled points used by a feature must be valid. Mean/min/max/range need one point, level standard deviation two, return both endpoints, volatility at least two adjacent returns. Gap/invalidity inside the window yields unknown until the bad points leave it. No interpolation, automatic history downloads or universal three-sample qualification. Raw last-trade values may be held only within their own pinned maximum age, never refreshed by unrelated book receipts. Trade ID/source time remains attached.
Raw crossing features explicitly declare mode=event and a named trigger stream. Grid-derived expressions may cross only on successive valid publications of their declared grid; that mode=grid crossing explicitly names the feature grid. Reject missing/mixed trigger-mode declarations. A crossing compares signed expression-minus-level values at adjacent valid observations/publications: above means previous<=0 and current>0; below means previous>=0 and current<0. Equality alone does not cross. Moving levels use each observation’s contemporaneous value. An unknown value or continuity gap resets prior evidence; a future valid pair is needed. A rolling crossing count uses the same declared crossing stream and receipt-time window (t-W,t], and requires uninterrupted declared continuity for the whole window. It cannot infer zero crossings across a gap.
Events, grid data and stored feature points are bounded: at most 10,000 retained points per feature and 320,000 total per evaluator; evict only points proven outside all required windows. Exceeding an in-window budget marks evaluation overloaded/unknown and blocks candidates instead of silently discarding evidence. No capacity or latency claim before measured checks. Trade volume uses the trade stream, not grid re-evaluations; its window also must be <900,000 ms. Unknown block-trade classification makes volume unknown. Actual feed acceptance/cadence is a later run-start check, not guessed at import; arithmetic durations/capacity are import checks.
A versioned engine validity profile supplies per-field maximum source age, cross-source maximum skew, continuity policy and adapter semantic versions. It is selected by the engine, stored immutably with a future run’s settings, included in evaluation evidence, and cannot be weakened by JSON. #4 tests inject an explicit controlled profile with stated numerical limits and acceptance expectations; no feed profile is claimed validated. Cross-source feature nodes require valid aligned inputs within that pinned skew bound or yield unknown. Changing a profile starts a new run, never reinterprets old evidence. Explanation names this profile dependency; no numerical production cutoff is invented by this proposal.

5. Conditions, side selection and checkpoints
Conditions support lt, le, eq, ne, ge, gt on compatible scalars, Boolean checkpoint references, and nested all/any/not. Maximum depth 8; at most 256 condition/feature nodes. Unknown propagates with three-valued Boolean logic: all is false if any child false, true if all true, otherwise unknown; any is true if any child true, false if all false, otherwise unknown; not unknown remains unknown. Only true qualifies. One strategy-wide required_sources set must include the transitive sources of every input, feature, checkpoint, selector and purchase branch; additional named supported sources are allowed and explicitly health-gated. All required sources must be available to start and healthy/fresh for any candidate purchase. ANY/OR combines conditions only and NEVER provides source failover; the preview states this prominently and lists the entire required set. Source fallback is unsupported; authors can create separate strategy versions/runs with explicit sources rather than silently substitute them. Branches have no independent required_sources declaration. Checkpoints need only their own transitive sources to be valid for latching; an already latched checkpoint retains its evidence through a gap, but its source remains in the global purchase health gate.
Deriving direction from BTC is optional. Every purchase branch must declare a side selector; omission is a validation error. Checkpoints may explicitly declare side-free Boolean mode, otherwise must declare a selector. Supported side selectors: fixed YES, fixed NO, evaluate both sides, choose from the sign of a named numeric signed-difference expression (positive YES, negative NO, zero no selection), or same/opposite of a remembered checkpoint side. Evaluating both sides selects only a unique true match; simultaneous true matches or unknown competing-side results yield no selection. Sign zero is a known no-selection result, so eligibility is false, not unknown. Missing numeric values give unknown selection and eligibility. Resolve the selector first, then evaluate selected-side conditions, then the buyable-ask condition. Evaluate-both-sides performs those checks for each side and requires exactly one true and the other known false; a tie or unknown competitor yields no candidate. No default preference and no both-side objective.
Every checkpoint/branch declares its trigger stream: one named complete source-event stream or one named feature-publication grid; unsupported/missing triggers are rejected. Current conditions and duration can use either; consecutive and first-event gates require a complete source-event stream; raw crossing uses its declared stream. A crossing of a grid feature uses grid publications and cannot be described as distinct source confirmation. Other-source updates refresh cached inputs but do not start or positively confirm a node with a different trigger. HOWEVER every dependency update, source/side invalidation, grid publication, expiry and gap must reevaluate negative evidence for any active duration or consecutive streak: false/unknown or a side change resets that incomplete evidence immediately, even on a non-trigger source. Only the declared trigger can start duration, advance a streak or confirm success. This invalidation path cannot latch a new checkpoint or invent an observation. Up to 16 named checkpoints, each with an observation interval, side selector if needed, condition and confirmation mode. A side-free checkpoint is just Boolean; same/opposite references to it are rejected. Checkpoints may reference only earlier declared checkpoints; no cycles. Process in declaration order on each observation, so a later checkpoint may see an earlier checkpoint latched on the same observation. Relative-side checkpoints are evaluated only after their source checkpoint exists. A later-event requirement must explicitly exclude that same event.
A checkpoint latches true once, retaining its first side, evidence time and event identity until the next market. It never unlatches when price changes, its interval ends or data disappears. An unlatched checkpoint cannot be invented from missing history. The default reset boundary is every new market; re-arming/unlatching inside a market is unsupported. Up to 16 checkpoints meets multi-stage use without arbitrary programs.
Confirmation modes (author selects parameters):
- current: condition true on this valid observation;
- consecutive: N distinct complete updates from an explicitly selected stream, for the same side, all qualifying; N 1–100. False, unknown, gap, source epoch change or side change resets the incomplete streak. Duplicate events and timer polls do not advance it;
- duration: condition true continuously for the author's duration with complete coverage; false/unknown/gap resets the incomplete duration. Every referenced input must remain within its original source-age bound for the entire interval; expiry timers invalidate evidence even without messages. An unrelated input update never refreshes that age. Non-trigger dependency failures reset as described above; only a declared trigger can restart or complete confirmation. Confirm only on a valid observation at/after the elapsed duration. “Continuous” means no observed failure or declared continuity/freshness gap, not proof of unobserved physical values;
- crossing: a defined crossing event; composable with other conditions.
A complete observation is a coherent snapshot after applying an ordered source update; independent identity is (source, connection epoch, source event/batch ID). Adapters must coalesce components of one provider action before emission where a provider boundary is documented. If distinct complete updates cannot be proven, consecutive/first-event rules stay unsupported for that adapter, never count timer calls or duplicate messages. Disclose this adapter acceptance gate; #4 tests use controlled complete events and do not claim provider proof.
After restart no market evaluation resumes automatically. Transient confirmation state resets; saved immutable strategy versions and history persist. Later run recovery/checkpoint persistence is owned by its later issue. Already latched in-memory checkpoints survive a temporary feed gap; new purchase evaluation requires current fresh inputs.

6. Purchase eligibility and time
Up to 8 ordered purchase branches. Each declares prerequisites, a mandatory typed side selector, condition, interval, event gate, trigger stream and an explicit buyable-ask band. Global required_sources covers their full transitive references; no per-branch source set exists. Only true with a uniquely resolved side yields a candidate. First eligible branch wins in declaration order; disclose order in explanation. No branch can initiate a second objective after a fill or switch a partially filled objective's side. All actual order/retry/partial-fill behavior stays engine-owned in later issues.
Intervals use elapsed milliseconds from market open, or from an explicitly named checkpoint, with inclusive start and exclusive end. All are intersected with the market’s [open,close) window; this declared intersection is displayed in the explanation, not silent coercion. Static market-relative empty intervals are rejected. A checkpoint-relative interval that becomes empty at runtime is expired and gives an explicit reason; no retrospective eligibility. Close-relative input/deadline is also available with the same explicit endpoints. Validate nonempty bounds; late-arriving observations are never evaluated retroactively for purchase. A timer can expire eligibility without a price update, but cannot create a new book event or freshness.
Event gate per branch is mandatory: current, first_after_checkpoint, or first_qualifying_after_checkpoint. All gates evaluate on their declared trigger only. Current allows repeated eligible observations during the interval; it never fabricates a provider event on a timer. Source-event first gates arm immediately after the referenced checkpoint latches, anchored by that checkpoint’s engine sequence (not provider time). The first complete event on the named source stream with greater engine sequence consumes first_after_checkpoint even before the branch interval starts, before another prerequisite exists, while health is bad, or while an earlier branch wins. This intentional unconditional consumption is disclosed in the preview: authors needing a later arming point declare another checkpoint to anchor it. Unknown or false conditions consume it as well. An anchor on stream A can target stream B; “after” means greater engine sequence. The anchor event itself cannot consume it.
First_qualifying_after_checkpoint waits for a subsequent named source event where all strategy eligibility is true: interval, prerequisites, uniquely resolved side, condition, buyable-ask band and global source-health/profile gates. Consumes when that full eligibility is reached; false/unknown do not consume. Runtime money/order/quantity authorization is separate and cannot defer or rearm a consumed gate. Every branch processes its gate independently before priority selects one candidate: lower-priority first-event or first-qualifying gates can therefore be consumed even if a higher-priority branch wins. Explanation states this. Explicit prerequisite checkpoints can stage conditions, but cannot observe branch selection and do NOT generally recover a lower branch consumed by priority. First-qualifying currently means first OBSERVED eligible event, not first SELECTED event; this is a pending owner choice listed below. Consumed opportunities never rearm in the market. A source continuity gap between anchor and the proven first event makes first_after_checkpoint unavailable for the rest of the market; first_qualifying can resume on new fresh evidence but cannot invent missed events. Duplicate receipts never consume or qualify. Timers can expire gates but cannot advance them. Close clips every deadline.
Strategy conditions can constrain any ask/bid/trade measurement, but the purchase branch also has an explicit buyable-ask price condition evaluated against its chosen side. The user's permitted range is an additional requirement; bid/last-trade matches cannot stand in for a buyable ask. Quantity, funds, fees, objective state, loss limits, recording, market eligibility, source access, freshness and stop/pause remain engine gates, never author-disableable. No exact current settlement behavior is inferred from spot; source/contract mapping remains an adapter acceptance requirement.

7. Bounded strict import and immutable versions
Maximum UTF-8 input 64 KiB, JSON nesting 16, 32 input declarations, 32 features, 16 checkpoints, 8 branches and 256 total expression/feature nodes. IDs 1–32 ASCII lowercase/digits/underscore, unique within their namespace; references resolved and typed. Name 1–80 bytes, optional author note <=1 KiB, no behavior-changing free text. Reject duplicate JSON keys, unknown fields/enums, unsupported format version, invalid/missing references, cycles, incompatible units, excessive counts/precision/ranges, nonfinite numbers, negative durations and malformed/oversized content. No silent dropping/coercion. Diagnostics identify field path/reason without rendering author content as HTML. UI uses text rendering.
Validation produces one typed representation used by evaluation and deterministic explanation templates. Explanation covers source/field/unit identity, computations and lookbacks, side/tie selection, threshold endpoints, branch priority, checkpoints/confirmation/reset, gaps, required sources and engine safeguards. Author notes are clearly separate and cannot replace it. Rule changes require a contract/evaluator version; saved versions retain their semantics and generated explanation. Reject unsupported old versions instead of reinterpreting them.
Preview validates and shows the explanation before saving. Saving appends a new immutable version with canonical JSON, contract version, generated explanation and creation time; edit means copy, modify, preview and append. Never update/delete prior versions or history. Duplicate imports may append another version (no deduplication feature). Results must later link to the exact version/settings. Existing session controls and stopped restart remain unchanged; no active financial run exists in this slice. Future active runs cannot swap their version.

8. Controlled examples and acceptance evidence
Use one synthetic worked example, with configurable illustrative constants, not old strategy thresholds:
A. During an author-selected interval, a named BTC/strike comparison and chosen side's ask band become true. Checkpoint A remembers the side; no purchase is required to establish A.
B. Later, the opposite side's BUYABLE ASK enters the author's price band (for example <=30 cents). Optional distinct-update or duration confirmation is chosen explicitly. Select that opposite side and require fresh data plus user price/settings checks. The “30 percent” display is a 30-cent contract quote, not a calibrated 30% win-probability claim.
D/E/F-style sequences are expressible as mechanics; no claim of reproducing all historical scoring/hedging or exact old rules. Explain bid-trigger versus ask-trigger differences; they are author choices, not presumed equivalent during spread/gaps.
Acceptance tests through engine public interface with controlled time/events and real disposable SQLite:
- Every operator/feature, type/unit check, precision boundary and resource bound; reject unknown/duplicate fields and unsupported inputs.
- Multiple checkpoints, same/opposite sides, simultaneous ties/unknown competitors, first-latched-side retention, same-event versus later-event gates, ordered branches.
- Exact start/end/deadline, timer expiry, stale/late/duplicate/out-of-order events, first-event consumption and first-qualifying behavior, moving-threshold crossings/equality.
- Consecutive and duration resets, complete rolling coverage, source gaps, no interpolation or replayed purchase; latched checkpoint survives gap but missing current data blocks candidate.
- Cross-source comparison requires coherent fresh timestamps under the run-pinned versioned engine validity profile; controlled tests state exact age/skew bounds and cover excess skew. Actual production profile acceptance belongs to future adapters, never an author override.
- Identical validated representation drives explanation/evaluation; representative boundary fixtures match the text. Canonical version and explanation survive edits/reopen; earlier history unchanged; schema migration preserves existing sessions; restart stopped.
- Focused IPC permission/storage tests and packaged Mac import -> preview -> save -> edit-copy -> save -> reopen using disposable workspace. No dummy-Keychain rerun unless its boundary changes.
Run current applicable CI/local checks and package build when implementation is authorized. Source entitlement/fees/exact settlement mapping, actual provider-event boundaries and performance capacity remain separate unproven gates, not exceptions to passing local semantics.

Additional controlled cases: interleaved cross-source events with identical source timestamps; fixed receipt-sequence replay; source data arriving after grid finalization; grid versus event crossings; first gate consumed before interval/prerequisites or while masked by branch priority; quote-expiry resetting duration without messages; sign zero versus unknown; canonical book ask versus native summary ask; dependency-source health including latched checkpoint sources; percent operand order and output scale, half-even ties, exact squared-root boundaries and fixed intermediate-limit unknowns. Record each oracle in the eventual tests; no implementation proof is claimed now.

Pending owner choices — do not imply these restrictions were requested or approved:
- Global purchase source health includes sources used only to establish an earlier checkpoint. Example: Coinbase established a checkpoint ten minutes ago; fresh Kalshi ask qualifies now, but a Coinbase outage blocks purchase. Keeping the checkpoint does not remove this global gate. This proposal's strict policy is consistent with one reading of required-source safety, but authors cannot express “observe this source once, then no longer require it.” Owner must accept that effect or choose separately declared historical-observation versus current-purchase source requirements. Fresh current inputs remain mandatory either way.
- No pre-open/cross-market feature history means a five-minute lookback cannot support a first-minute purchase. Preview MUST compute/display the earliest possible ready time for each feature and dependent branch, explain warm-up, and diagnose intervals that expire before readiness. Supporting early-window lookbacks would require bounded pre-open observations as a separate approved scope choice; it does not inherently require downloads. No exact prior-market comparison is promised here.
- First-qualifying is currently first observed eligibility, consumed even when branch priority masks selection. If the owner wants first selected eligibility, only the winning branch should consume this gate; literal first-after-event remains unconditional. No generic “extra checkpoint” workaround is claimed. This behavior choice stays explicit until accepted.
These choices are disclosed design restrictions, not implementation findings. They remain unapproved; no code resumes from this text alone.

9. Recommendation to owner
Approve the supported vocabulary and bounded semantics, including the explicit scoring/long-history limitations, before code resumes. The expanded measurement set is more work than the unfinished one-input grammar; it is proposed openly as the smallest documented common engine vocabulary for the owner's requested flexibility. Do not build provider integrations or add strategies as part of this approval. If this scope is too large, reduce the vocabulary explicitly rather than accept JSON that does not work.
