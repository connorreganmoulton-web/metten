## Prioritized findings

All dispositions below are synthesis recommendations awaiting owner alignment with the brief. They do not represent new owner-approved decisions. Exact mechanisms remain engineering work.

### 1. Preserve meanings as well as saved files — Major

**Lenses:** architecture, simplicity, compatibility, maintainability.  
**Evidence:** hypothesis “Preserved boundaries”; handoff example 12; specification §§4, 7, 10, 12; glossary “Strategy version”; `crates/engine/src/storage.rs`, `strategy_versions()`.

Saved JSON is currently reparsed and its explanation regenerated by the current parser. An engine update could therefore change an old explanation or make stored versions unreadable without changing any row. The existing same-implementation reopen check does not prove compatibility across a changed contract.

**Recommended disposition:** identify the rule meaning used by each version, retain original records, and preserve historical interpretation. Unsupported historical versions should remain inspectable without making all other versions disappear. Conversion creates a new version. Choose execution compatibility only where needed; preserving every draft evaluator forever is not required. Missing proof: earlier-format fixtures and mixed supported/unsupported versions across a contract change. Actual saved private workspace contents were not inspected.

### 2. Keep evidence local to its conditions and process it coherently — Major

**Lenses:** architecture, simplicity, maintainability, inventive catalyst.  
**Evidence:** handoff B–E, examples 1, 3–5, 7–11; specification §§4–6, 16; ADR 0001; draft `Evaluator::observe`.

A global all-inputs-valid gate would block independent alternatives and completed checkpoints. Latest-value-only processing could erase a failure or crossing. Separate feature resets could erase useful underlying history or overlook quantity/side restrictions.

**Recommended disposition:** distinguish accepted observations, current validity, historical coverage, remembered checkpoints and purchase-objective state. Specify their lifetimes and one coherent evaluation order, including checkpoint-before-purchase and jointly updated derived results. Preserve the settled startup/recovery distinction. Missing proof: the twelve controlled examples through the same public evaluation contract. Actual adapter ordering and durable purchase recovery belong later.

### 3. Bound the accepted workload without trimming agreed capabilities — Major

**Lenses:** architecture; UX supports actionable limit errors.  
**Evidence:** handoff A, D, E; specification §§2, 10, 16.

A small file can request expensive nested rules and retained history. Unbounded processing threatens local responsiveness; continuous raw-feed persistence would conflict with the baseline.

**Recommended disposition:** engineering must justify import and retained-state limits, reject excess clearly, and preserve the agreed capability families and hour-long underlying lookbacks. Do not inherit arbitrary old budgets or impose a market-length history cap. Missing proof: justified concrete bounds; later measured concurrency/capacity remains issue #16.

### 4. Explain rule structure and specific waiting reasons — Major

**Lenses:** operational visibility, UX.  
**Evidence:** handoff B–E, examples 1, 3, 6–10; specification §§10–12.

A flat condition list or generic “waiting” message can conceal priority, remembered evidence, missing history, or the shared quantity ceiling.

**Recommended disposition:** generated explanations should show preferred/alternative structure and common objective restrictions. Controlled decision results should distinguish unmet conditions, unavailable evidence, priority selection and common safeguards. Preserve the startup labels and distinguish a recovered current snapshot from an unresolved historical hole. Record meaningful local transitions and summarize repeated reasons. No remote telemetry, continuous raw feeds or new dashboard implementation is required in #4. Missing proof: representative generated explanations and controlled reason outcomes; later issues connect these to trading history.

### 5. Make rejected imports repairable and separate validity from access — Major

**Lens:** UX.  
**Evidence:** hypothesis “Anchored hypothesis”; handoff acceptance criteria and engineering-definition section; specification §§3, 9, 12.

Generic errors transfer diagnosis to authors. A valid-rule result could also be mistaken for proof that a named provider is accessible.

**Recommended disposition:** identify the offending field/rule and accepted form, preserve the user's correction path, and distinguish supported rules from later source readiness. Do not require account access to author or import supported rules. Missing proof: diagnostics for malformed input, unknown operators, incompatible units/source pairings and justified resource limits.

### 6. Establish history feasibility without guessing contract lifetimes — Major

**Lens:** UX; synthesis qualification below.  
**Evidence:** handoff A, D, example 11; specification §2.

History belongs to an identified underlying or contract. A requested lookback may be impossible under a particular collection/identity contract, and “collecting” must not imply that an impossible requirement will eventually succeed.

**Recommended disposition:** define history identity, collection start and eligibility. Reject only demonstrated impossibility and explain it; never join successive contract books to satisfy a lookback. Preserve long underlying history and feasible contract measurements. The raw UX report suggests that a newly opened 15-minute contract cannot supply an hour of history. A 15-minute outcome window alone does not establish listing or observable-book lifetime, so that universal inference is not adopted. Missing proof: collection semantics and controlled feasibility examples; actual provider capability is later evidence. No owner scope contradiction has been established.

### 7. Preserve the workspace when formats change — Major

**Lens:** compatibility.  
**Evidence:** specification §§6, 10; handoff preservation requirements; draft storage `Recorder::open()` revision check.

New strategy contents could become unreadable to an older application even if the database structure is unchanged. Failed upgrades must not damage existing records.

**Recommended disposition:** use atomic storage changes and an explicit compatibility/refusal policy. An older app may explain that a newer workspace needs a newer version; silent reinterpretation, downgrade or deletion is unacceptable. A general downgrade system is unnecessary. Missing proof: disposable prior-workspace and interrupted-migration checks after the stored contract is defined.

### 8. Reuse the existing application boundaries — Nit

**Lens:** simplicity.  
**Evidence:** draft engine import/list methods, Tauri `strategies`, frontend import/edit-copy flow and `examples/learning.json`.

Adapt the existing local import and version plumbing. The draft's global validity, mandatory checkpoint and single purchase-expression restrictions cannot become requirements. Resolve preview-before-save in the detailed flow. A visual builder, plugin system, second evaluator, external explanation service or documentation platform is unwarranted.
